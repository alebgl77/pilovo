# Pilovo contract — 0.4.0 Preview

`src/shared/types.ts`, `src/shared/web.ts` and `src/shared/activity.ts` define the client and activity contracts. The extension has no backend, model API or active native connector. Historical companion source remains unbundled reference material.

## Activity observation

Required permissions are exactly `storage`, `sidePanel`, `alarms`, `scripting`. Optional hosts are exactly `https://claude.ai/*` and `https://chatgpt.com/*`, requested individually. Unreleased: the only optional API permission is exactly `notifications`, for [optional OS notifications](#optional-os-notifications); the 0.4.0 manifest declares none. There is no required host access, broad `tabs`, `management`, `nativeMessaging`, required `notifications` or static `content_scripts` declaration.

After a grant, the worker dynamically registers the bundled `observer.js` in the isolated world with session-only registration. Content hints request resampling; they do not supply a trusted state or arbitrary page text. Validate schema, extension sender, permitted origin, tab and top-level document, activation/session identity, monotonic sequence and sample request identity. Late messages from navigation or an old activation must be rejected. Page data is untrusted.

Only bounded, recognized controls/status indicators are sampled. No full prompt/response, tab title, screenshot, cookie or credential is collected. Activity metadata remains ephemeral; no activity history is persisted/exported. Internal database/source/protocol identities, including `agent-control-hub-v1` and `hub.rpc`, remain stable.

Each observation has provenance `observed_ui`, local observed time and expiry. Working requires recognized evidence. Response-ready attention requires witnessed working followed by stable ready evidence after debounce; an idle composer, removed control or old completion announcer alone is insufficient. Only explicitly recognized intervention/error indicators produce their respective attention reasons. Absence, ambiguity, navigation or expiry yields unknown. Completion never verifies task success.

The observation lifetime and authorization lease are at most 15 seconds logically. Revocation invalidates state, stops lease renewal and unregisters observation. Suspended pages can execute cleanup late but expired leases cannot authorize fresh sampling. Restart discards activity and requires fresh evidence. Chrome throttling may cause unknown states.

Focus revalidates the provider/tab association and activates its tab/window. It does not change execution. Seen acknowledges one local attention identity; it is not approval, task verification or provider control. There are no stop/pause/resume/launch commands.

Unreleased: optional automatic seen. `settings.autoAcknowledgeSeconds` is exactly `0`, `5`, `15` or `30`; `updateSettings` refuses any other value with `validation.invalid`. `0`, the default, turns it off, and is also what settings stored before this field existed read as, by merging the stored record over the defaults without migration; export schema 2 carries the field. The worker reads it at startup and after each `updateSettings`, with the same ordered application as the language. While it is on, the user is viewing an attention when its tab is the active tab of its window and that window is Chrome's focused window; the panel itself, side panel or full page, never counts in place of that tab. The worker follows this through `windows.onFocusChanged` (`WINDOW_ID_NONE`: Chrome lost focus) and tab replacement events, which stop any dwell at once, and through `tabs.onActivated`, `tabs.onAttached` and `tabs.onDetached`, which stop it unless the event concerns neither the viewed tab nor the viewed window: activating or moving a tab in a background window cannot change the focused window's active tab, so a running dwell keeps its start (a focus change has its own event, and the deadline query covers a missed one); after a stop, only while the setting is on, it asks `windows.getLastFocused()` and `tabs.query({ active: true, windowId })`, reading window and tab IDs and the `focused` and `active` flags only, without the `tabs` permission or page access. A dwell starts when an unacknowledged live attention's tab becomes viewed, or when a new attention identity is raised in the viewed tab; there is at most one, a worker timer that never outlives the worker. It stops on a tab or window change, navigation or a new document or activation, tab closure, a new attention identity, acknowledgment, expiry, revocation or a setting change, which restarts it from the currently viewed tab. At the deadline the worker asks Chrome again, then checks in one synchronous step the same record identity and attention identity, still unacknowledged and live (`validUntil` after now), the grant still enabled, and the tab still viewed both in that fresh answer and in its event-maintained view; only then does it acknowledge exactly that attention identity through the ordinary seen path, whose change repaints the badge. This is a local acknowledgment after dwell, off by default: never verification, approval, task success or provider control. The view and dwell are memory only, never persisted, exported or sent.

Each new attention identity records `raisedAt` on the monotonic clock used by `validUntil`; a persisting attention keeps it. Unreleased keyboard commands reuse these rules. `focus-next-attention` (suggested `Alt+Shift+J`) selects the live, unacknowledged attention raised first, with the lower tab ID on ties, and runs the same focus revalidation; the fresh sample must also still show that unacknowledged attention. A failed attempt moves to the next of the initially selected candidates, never looping. With no candidate, it opens the side panel synchronously within the command gesture, in the command's window or else the last focused browser window (a numeric window ID kept in worker memory); after every candidate failed it tries the same, best effort, since Chrome may no longer accept the gesture. `acknowledge-all-attention` (no default key) and the panel's mark-all action are local seen only, identical to acknowledging each current identity. The panel sends the identities it displayed, so attention raised later stays unacknowledged. Manifest commands are not permissions and carry no page data.

Each observation also carries `stateSince` on the same monotonic clock: when its current state began within the current record identity. Samples that keep the state keep it, including the response-ready debounce, during which the state stays working. A state change resets it; a new attention identity resets it together with `raisedAt`, to the same value, even when the state stays attention. Unknown evidence, a failed sample (`unavailable`) and expiry reset it through the unknown state, and navigation, a new document or activation and a worker restart start a new record. Unreleased: the panel shows working and attention rows, seen or not, with an elapsed duration derived from it (`monotonicEpoch() - stateSince`, minute precision, plain text without a live region); idle and unknown rows, and a negative or non-finite value, show none. Durations are never persisted, exported or sent. They are a consequence of the conservative evidence model: they restart whenever the worker loses evidence, so they measure continuous observation by this worker, not provider generation time. The panel's own downgrades to unknown (a failed read, a snapshot reporting `unavailable`, a pending grant change) leave `stateSince` untouched: they hide the duration, which returns unchanged when fresh worker data confirms the same record.

Unreleased: each observation also carries tab-level identity, which the worker keeps beside its evidence records and adds to every snapshot. `sessionNumber` is per provider: when a tab is first observed in this worker life, it receives the smallest positive integer that no other open tab of the same provider holds, and keeps it while that tab lives, including across navigation, reloads, new documents or activations and expiry, which replace the record but not the tab. Tab closure, revocation of that provider and the tab leaving that provider (no longer eligible for it, including a switch to the other provider) release it; a returning tab is numbered afresh. A worker restart restarts numbering. The panel shows this number and never computes its own, on named rows too (“Revue contrat — Claude · session 3”), since it is what OS notifications name. `tabIndex` is Chrome's 0-based `Tab.index`, readable without the `tabs` permission; it is refreshed on each committed sample and re-read for observed tabs (index and window only, without page access) whenever a tab is created, removed, moved, attached or detached, and is absent until read. The panel shows it 1-based (“Onglet 4” / “Tab 4”) and adds “autre fenêtre” / “other window” only when `chrome.windows.getCurrent()` reports the panel's own window and it differs from the observation's; the preview has no such reading and omits it. `label` is typed by the user through the strict `labelWebActivity { id, label }` RPC: a string that, once trimmed, has 1 to 40 characters and no C0/C1 control character or bidi embedding, override or isolate character (U+202A–U+202E, U+2066–U+2069), or `null` to clear; anything else, including extra fields, fails with `validation.invalid`. As for focus and seen, the ID must name a live observation, one the worker currently holds with unexpired evidence, otherwise `navigation.expired`; the panel offers renaming only on such rows. A label is bound to the tab's lifetime, not to the document or the session number: it is kept across navigation in that tab, including the tab leaving its provider and coming back, and appears only on observations of the provider it was given on, so it never moves to the other provider. It is removed with the tab's closure or replacement, the revocation of that provider or a worker restart. It exists only in worker memory: never persisted (no IndexedDB, no `chrome.storage`), exported, sent, or placed in the badge, its title or any notification, and it appears only on its own tab's observation. The panel renders it as a text node, never as HTML. None of these fields carries a tab title, URL or page content.

The toolbar badge counts last-observed, unacknowledged attention. Unreleased: it is computed from live (unexpired) observations only. With unacknowledged attention, the count sits on the color of the most urgent reason present (`error_visible` > `input_required` > `response_ready`); otherwise a live working observation shows `…` (U+2026) on neutral gray, without a count; otherwise it is empty. Acknowledged attention, idle and unknown never light it. Every background carries white text at a contrast of at least 4.5:1. The action title states the same counts in text, omitting zero parts: `Pilovo — 3 à vérifier, dont 1 erreur visible · 1 en cours` / `Pilovo — 3 to review, including 1 visible error · 1 working`, `Pilovo — 2 to review (responses available)` when every item shares the most urgent reason, or `Pilovo` when nothing counts. It follows the app's own `settings.language` (default French), which the worker reads at startup and after each `updateSettings`, not the browser UI language; its strings are a fixed worker-side FR/EN table because `chrome.i18n` cannot switch language at runtime. Badge and title contain only counts and fixed reason words: never a provider, title, URL, label or content. Unchanged values make no `chrome.action` call. Freshness is re-evaluated by the panel and background watchdog. Expiry lowers or clears the badge through that watchdog and the periodic activity alarm, best effort under MV3 scheduling; if the watchdog runs before the earliest deadline, it re-arms instead of waiting for the alarm. Revocation and tab closure remove the affected rows' contribution as soon as Chrome delivers the event, and a worker restart repaints the badge hidden before any fresh evidence. No strict real-time guarantee is made, for the badge or for optional OS notifications. See [compatibility](compatibility.md).

## Optional OS notifications

Unreleased, off by default. This is the reviewed scope proposal that replaces the former boundary of no OS notifications, which still holds for the 0.4.0 release, with an opt-in, bounded one.

Permission. The manifest declares `optional_permissions` exactly `["notifications"]`; it is never required, and `package:check` (with its `test:publication` unit tests) refuses any other optional permission. Only the panel or full page requests it, with `chrome.permissions.request({ permissions: ['notifications'] })` called synchronously in the change event of the settings checkbox that enables the first service, so Chrome sees the user gesture; the worker never requests it. A refusal leaves the setting unchanged and is announced in an alert. Unchecking the last service saves the setting, whose `updateSettings` reply waits until the notification clears that change caused have reached Chrome (2 s at most), then calls `chrome.permissions.remove` for it, best effort: once the permission is removed, Chrome refuses notification calls, clears included.

Setting. `settings.notifyProviders` lists distinct services among `claude-web` and `chatgpt-web`; empty, the default, turns notifications off. `updateSettings` refuses duplicates, unknown services, non-arrays and extra fields with `validation.invalid`; settings stored before it existed read as empty through the same merge over the defaults, without migration, and an unexpected stored value reads as empty. Export schema 2 carries it. The legacy `notifications` flag is unrelated: it belonged to the historical native agents and stays `false`. The worker applies the list at startup and after each `updateSettings`, under the same ordered settings application as the language and automatic seen. The panel shows a service as notifying only while the setting lists it and `chrome.permissions.contains` confirms the permission, read again with every snapshot; a permission removed elsewhere (Chrome's extension settings) therefore reads as off, with an explanation, and checking a service requests the permission again for that service only. The browser preview has no permission methods: its checkboxes are disabled and say why.

When. The worker creates at most one notification per attention identity, at the committed sample where the reducer raises that identity, and only if its service is listed, `chrome.permissions.contains({ permissions: ['notifications'] })` is true and its tab is not viewed: not the active tab of Chrome's focused window, read by a fresh `windows.getLastFocused()` and `tabs.query({ active: true, windowId })` as for automatic seen (IDs and flags only; a failed query counts as not viewed). After these asynchronous checks it re-checks in one synchronous step the same record identity and attention identity, still unacknowledged and live, the same grant, the service still listed and no change of that service's setting or of the permission meanwhile. Attention raised before its service was listed is never notified, even if the service is removed and added again during the checks. An identity raised again with the same reason, in the same tab and service, with only unknown, failed or expired evidence since the previous one (a throttled background tab whose evidence lapsed, for example) is the same condition again and is not notified twice; a notification still in its grace period (below) stands for it instead. Observed work or idle evidence, another reason, navigation (including a tab frozen, discarded or moved to another window, which also clears its notification), tab closure or a worker restart ends that run. An activity alarm that wakes the worker, or a host access grant, starts observation only after the stored settings apply, as startup does, so attention sampled first is never mistaken for attention raised before its service was listed.

Content. `type: 'basic'`, the extension's 128 px icon, `title` the service name (`Claude` or `ChatGPT`), `message` the reason followed by ` · session N` with the worker's session number (`Réponse disponible`, `Intervention demandée`, `Erreur visible` / `Response available`, `Input requested`, `Error visible`), `contextMessage: 'Pilovo'`, `priority: 0`, `requireInteraction: false`, no buttons. Like the badge title, the words come from a fixed worker-side FR/EN table that follows `settings.language`, because `chrome.i18n` cannot switch language at runtime. A notification never carries a session label, tab title, URL or page content.

Identity and lifetime. The notification ID is `pilovo:<observation id>:<attention id>`, both worker-generated UUIDs. The worker keeps its live notifications in memory: at most one per tab (a newer attention replaces the previous notification) and 16 in all (the oldest is cleared first), and it remembers up to 256 notified attention identities. A notification is cleared as soon as its attention ends: acknowledgment (manual, mark all or automatic seen), replacement by a new identity, navigation or a new document or activation, tab closure, revocation of that service's host access or the service leaving the setting. Evidence that only lapses (expiry, a failed sample or a sample without a recognized signal, as in a throttled background tab between the 30 s activity alarms) starts a grace period of 35 s instead: if a committed sample raises the same reason again in that tab, as a new identity, unacknowledged and live, with the same grant and the service still listed, the notification stands for that identity from then on, keeping its ID and text without another Chrome call, and that identity counts as notified; observed work or idle, another reason, navigation or the end of the grace period clears it. Create and clear calls are serialized, so a clear never overtakes the creation it undoes. `chrome.permissions.onRemoved` reporting `notifications` cancels pending checks and makes the worker forget its notifications; since Chrome then refuses notification calls, it cannot clear the ones already shown (the operating system may keep them until the user dismisses them), which is why the Settings page clears through the setting first. When `chrome.permissions.onAdded` reports `notifications` again, the worker clears the `pilovo:` notifications that `chrome.notifications.getAll()` lists and it does not hold. Chrome keeps an extension's notifications while its service worker is stopped; since a restart discards activity, each worker life clears once the `pilovo:` notifications that `chrome.notifications.getAll()` still lists from a previous life, and never recreates them.

Click. `chrome.notifications.onClicked` parses the ID strictly and ignores a malformed one. Otherwise it clears that notification and runs the ordinary `focus(observationId, attentionId)` for the attention identity it currently stands for (the one in its ID, or the one it was rebound to after a lapse): a fresh sample revalidates the provider/tab association and must still show that attention, unacknowledged, before the tab and window are activated, as for the next-attention command. A notification in its grace period first has its tab sampled; if, within 3.5 s, that sample raises the same reason again under the grace conditions above, focus runs for that identity, otherwise the click fails. On failure nothing more happens; the side panel is not opened, since a notification click is no reliable user gesture. A click is never a seen acknowledgment. `onClosed` forgets the notification. `chrome.notifications` is absent until the permission is granted, so these listeners are added at startup when it is granted and when `chrome.permissions.onAdded` reports it.

Limits. The operating system decides how a notification is displayed, grouped, silenced or kept in its notification center, and may retain or mirror a copy under its own settings; Pilovo only creates and clears it through Chrome. Delivery follows the sampling cadence and Chrome's background scheduling: no real-time guarantee. A notification is a prompt to look, never verification, approval, task success or provider control.

## Manual web preparation

`WebPreparation` remains distinct from observed activity and legacy receipts. Its provider selects only Claude or ChatGPT's fixed official origin. States `prepared`, `sent_by_user`, `completed_by_user` are human declarations. Copy/open/focus never imply submission, running or successful completion.

Prompt retention requires per-record consent, off by default. Without it, the form can copy unsaved text; storage includes title/provider/manual status, identifiers/timestamps and separate note/mission association. Explicitly setting legacy `retainPrompts` false erases retained web and historical prompts. No prompt travels in a URL or is submitted by Pilovo.

Discovery exposes provider/tab presence through host access, not account, subscription or model detection. Revocation clears permitted metadata; unknown presence does not mean no account. Refusal leaves fixed official-home-page navigation available.

## Persistence and historical provenance

IndexedDB version 4 preserves history under the same identity and adds a positive integer `revision` to web records, backfilled for version 3. Updates require `expectedRevision`; stale writes fail with `preparation.conflict`. Prompt erasure and mission detachment advance affected revisions. The UI clears stale prompt text and requires reopening; it must not silently rebase erased content.

Export schema 2 contains saved legacy/web data. Retention defaults to 30 days while active. Purge removes saved history but retains settings and minimal historical anti-replay identities; uninstall removes those too. Exports and provider history are separate.

Historical source/run IDs, receipts, reviews and scoped file checks retain provenance and are not converted to current activity. Legacy native capabilities remain disabled regardless of old settings. A SHA-256 check compares selected bytes to a supplied reference without proving reference authenticity or task quality; file bytes are not persisted/uploaded.

The source archive retains historical companion code/tests. The default build and Chrome archive exclude it. [Release checks](RELEASE.md) separate current validation from historical evidence.
